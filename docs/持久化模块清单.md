# 持久化模块清单

这份清单记录正式版本会写入磁盘、进入正式存档，或改变旧存档引用含义的数据。当前结构以 beta6 提交 `6675f77` 为基线；Git 历史审计覆盖 beta1 至 beta5。维护者已确认支持 beta1 至 beta6，并从 beta6 起为每个发行版保留兼容记录和样本。

表格只保留开发迁移功能所需的信息：版本、存储和实现位置、必要内容，以及一句话功能说明。测试目录、调试缓存和源码生成工具不在清单内。

版本栏中的“随 World”表示该区段没有独立版本号，只能依赖 World 外层版本识别；“无版本”表示当前磁盘格式没有可用于迁移分流的版本字段。

## 历史版本基线

beta1 至 beta6 的主版本组合均为：World v2、manifest v3、profile v2、Agent v3、居民二进制 v2、居民运行状态 v6、居民记忆聚合 v6、Provider v2、worldData v4。版本名和这组版本号都不能单独识别存档，必须同时比较字段、路径和指纹。

| 版本 | Git 基线 | World 区段 | 活动指纹 | 路径与本机数据差异 |
| --- | --- | --- | --- | --- |
| beta1 | `f81be45` | 26 个，无 `travelerRelations` | `584ba4b89019f92378131a56bc380e0c2dec5e460d977d7050484996a9c57a9f` | 居民工作副本和槽位协调目录直接使用原始 ID；Provider v2 无 `insecureHttpConsentEndpoint`；无 Web 设备标识。 |
| beta2 | `1569ab5` | 26 个，无 `travelerRelations` | `584ba4b89019f92378131a56bc380e0c2dec5e460d977d7050484996a9c57a9f` | 超长居民 ID 和槽位协调目录改用哈希段，新增 `_claims/`；Provider v2 增加 `insecureHttpConsentEndpoint`；无 Web 设备标识。 |
| beta3 | `99b5ab1` | 27 个，增加可选的 `travelerRelations` v1 | `70dcd511461e5266174f3ddb5323d2adf4ecd5caf38cf25d7ba886ead3e3b818` | 保存入口兼容 beta1 的旧槽位协调路径；无 Web 设备标识。 |

### 识别结论

- 正式存档本体只能稳定识别两组契约：beta1–beta2 的 26 区段契约，以及 beta3–beta6 的 27 区段契约。
- 完整用户目录可借助原始或哈希路径缩小 beta1、beta2 的范围；`web_device_id` 只在 Web 环境出现，不能用于确认 beta5。
- 历史 beta3 至 beta5 存档仍无法只靠旧字段准确区分。beta6 新写入的存档用 `saveRelease` 标记写入器版本；没有该字段时，检查结果必须保留版本范围，不能猜测具体发行版。
- 历史样本用样本元数据记录准确发行来源。后续发行版必须在存档中加入稳定的写入器版本或持久化契约 ID。

### 相邻版本处理声明

| 版本边 | 严格迁移内容 | 其他处理 | 声明依据 |
| --- | --- | --- | --- |
| beta1→beta2 | 正式存档无需迁移。 | 运行时记忆工作副本按新路径重新生成；旧锁、claim 和临时事务不迁移；Provider 配置尽力兼容。 | World、Agent 正式载荷未变，路径和 Provider 差异不属于强制存档升级。 |
| beta2→beta3 | 执行已登记的 `2026-08-12-public-dining-day-routine` 指纹迁移。 | 缺少的 `travelerRelations` 由当前恢复逻辑重建默认状态。 | 活动指纹变化；`travelerRelations` 是可选区段，无需虚构独立迁移函数。 |
| beta3→beta4 | 无需迁移。 | 按当前格式重新保存即可。 | 主版本组合、World 区段、活动指纹、路径和独立本机数据均未发现变化。 |
| beta4→beta5 | 正式存档无需迁移。 | Web 设备标识不迁移；World 代码拆分和 `privateMessages` 移动不改变磁盘格式。 | 严格迁移范围内的字段、版本、路径和指纹均未变化。 |
| beta5→beta6 | 无需迁移。 | 按 beta6 严格校验后发布新修订。 | 审计范围内的字段、版本、路径和指纹均未变化。 |

以上声明来自发行源码审计。仓库已经保存 beta1 至 beta6 的 8 份发行写入器重建样本，并通过文件、哈希和语义校验；这些样本不是玩家原档，完整的升级验收仍需等待导入模块实现，详见 `docs/历史存档样本.md`。

## 开发必须遵守的约束

1. beta1 至 beta5 不能只靠发行名称识别，必须用 manifest、World、Agent、居民状态、数据版本、指纹和目录布局组成版本组合。
2. 历史格式只能做宽松识别；迁移完成后必须按 beta6 当前格式严格校验。
3. World、Agent、world log 和 session config 必须保持相同的 `slot_id`、`session_id`、`save_revision`、World 修订和居民集合。
4. 迁移必须在临时位置完成，成功校验后发布新修订，不得原地改写 beta1 至 beta5 的原始存档。
5. 未知的更高版本、无法识别的版本组合、缺失迁移链和实际损坏必须使用不同错误结果。
6. 每条迁移必须逐版本执行、可以重复运行，并记录迁移前后版本、指纹和已应用迁移 ID。
7. 修改本清单中的字段、版本、存储位置或静态引用时，必须同时提交迁移规则或“无需迁移”声明、历史样本回归和本清单更新。
8. 真实样本至少覆盖 beta1 至 beta5 的空闲、活动中、未完成任务、已结算效果、自定义居民、居民记忆、world log、照片和 Windows 长路径状态。
9. 停止支持旧版本只能由维护者明确修改兼容范围并记录保全方式，不得静默删除已发布迁移。
