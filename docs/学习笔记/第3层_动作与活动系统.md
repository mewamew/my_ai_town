# 第 3 层：动作与活动系统精讲（新架构版）

> 目标：理解"居民能做哪些动作、动作从提交到结算的完整生命周期、活动系统怎么协作"，
> 以及**加一个新动作（或新玩法）的全链路检查清单**。
>
> 对应文件（新架构）：
> - 动作域：`game/world/runtime/action/`（19 个模块）
> - 活动域：`game/world/runtime/activity/`（24 个模块）
> - 合同侧：`game/agent/contract/AgentContractAction.gd`
> - 结果契约：`game/world/contract/TownWorldResultShapes.gd`
>
> **架构变化**：旧版动作处理散在 `TownWorldRuntime.gd` 的七张平行分派表里，类型集合不一致；
> 新版用 `TownActionTypeRegistry` 固化了单一事实源，并拆出独立的 Validation/Preparation/
> Preview/Advancement/Settlement 模块。

## 1. 动作类型全景（20 种，单一事实源）

**权威表**：`world/runtime/action/TownActionTypeRegistry.gd` 的 `ALL_TYPES`：

```
去 / 用道具 / 做活动 / 调整营业 / 托人传话 / 发布公告 / 待着 /
搭话 / 答话 / 争执 / 攻击 / 暗杀 / 制服 / 投票放逐 / 使用技能 /
追踪 / 查案 / 回应冲突 / 介入冲突 / 离开冲突
```

**七张分派表的统一**（该文件注释原文维护的知识）：
| 表 | 语义 | 权威位置 |
|---|---|---|
| T1 | ACTION_FIELDS 字段白名单 | `action/TownActionValidation.gd`（全集权威源） |
| T2 | `_prepare_action` 准备/分流 | `TownWorldRuntime`（准备入口）+ `action/TownActionPreparationRuntime.gd` |
| T3 | invalid_action_fingerprint 拒绝去重指纹 | `action/TownActionValidation.gd` |
| T4 | validate_action_shape 形状校验 | `action/TownActionValidation.gd`（必填校验只覆盖 8 类，字段白名单全覆盖） |
| T5 | `_advance_actions` 分钟推进 | `TownWorldRuntime` + `action/TownActionAdvancementRuntime.gd` |
| T6 | `_action_still_valid` 推进期有效性 | `action/TownActionValidityPolicy.gd` |
| T7 | default_doing UI 文案 | `action/TownActionProjection.gd` |

**关键结论（2026-08-07 逐条验证，写在注册表注释里，勿当 bug 去改）**：
- **冲突五类**（争执/攻击/回应冲突/介入冲突/离开冲突）：由冲突桥即时结算，
  全程不写 `resident["currentAction"]`，**永不进入推进循环**——不出现在 T4/T5/T6/T7 是**有意且正确**的
- **"做活动"**：经 `_prepare_action` 硬拒，必须改走 `activity.perform`（活动提交管线）
- **"用道具"**：在 `submit_agent_decision` 上游被分流到旧道具活动活路径
  （`action/TownLegacyPropActivityRuntime.gd`），T2 硬拒只守直连入口。
  **用道具是活玩法，其实现链不得删除**
- 测试守护：`tests/town_world_action_type_registry_test.gd` 逐表比对，防差集漂移

## 2. 动作生命周期（action/ 19 模块地图）

```
提交 submit_agent_decision (runtime/agent/TownAgentDecisionSubmissionRuntime.gd)
  │
  ├─ 形状校验      action/TownActionValidation.gd（T1 字段白名单 + T4 必填校验）
  ├─ 准备分派      action/TownActionPreparationRuntime.gd + runtime/agent/TownAgentDecisionActionRuntime.gd
  │                （特殊动作各自分流：做活动→activity 域；用道具→TownLegacyPropActivityRuntime）
  ├─ 确认预览      action/TownActionPreviewRuntime.gd（装预览→推进→激活→释放）
  ├─ 激活事务      action/TownConfirmedActionActivationRuntime.gd（真正生效：继续/替换/冲突入口）
  ├─ 分钟推进      action/TownActionAdvancementRuntime.gd（T5）+ TownActionValidityPolicy.gd（T6 有效期）
  │                + 各动作专项：TownWaitActionAdvancementRuntime / TownPropActionAdvancementRuntime
  │                + 移动专项：movement/TownGoActionAdvancementRuntime.gd
  └─ 结算          action/TownActionSettlementRuntime.gd（完成/中断）
       └─ 结果入队 action/TownActionResultRuntime.gd → event/TownWorldEventDeliveryRuntime.gd
```

**动作结果只有 4 态**（`world/contract/TownWorldResultShapes.gd`）：
`completed` / `rejected` / `interrupted` / `replaced`

**纯规则 vs 副作用提交的拆分模式**（整个新架构通用）：
- 判断放 Policy/Projection/Validation（无副作用，可独立测试）
- 执行放 Runtime/Command/Commit/Settlement（有副作用，按固定顺序提交）
- 例子：`TownActionValidityPolicy.gd`（纯判断）+ `TownActionAdvancementRuntime.gd`（推进提交）

## 3. 活动系统（activity/ 24 模块地图）

活动（"做活动"）走独立管线，不与普通动作混：

```
候选预检  activity/TownActivityCandidatePreflightRuntime.gd + Policy
          （预约冲突/缓存路线/区域占用/布局覆盖，TownActivityReachabilityCache 可达性缓存）
  │
  ├─ 可用性      activity/TownActivityAvailabilityRuntime.gd（睡眠/职业/任务/公告/天气中断）
  ├─ 提交/激活   activity/TownAgentActivitySubmissionRuntime.gd / TownActivityStepExecutionRuntime.gd
  ├─ 生命周期    activity/TownActivityLifecycleCommitRuntime.gd（工作结算/任务释放/公告/结果/信号提交顺序）
  ├─ 出席        activity/TownActivityAttendanceRuntime.gd（睡眠离岗/返岗）
  ├─ 例程        activity/TownActivityRoutinePolicy/State/ActivationRuntime/SettlementRuntime
  │              （多步骤例程：身份/结束分钟/确定选择/首步时长）
  ├─ 工作绑定    activity/TownActivityWorkTaskBindingRuntime.gd（活动开始时匹配工作）
  ├─ 完成结算    activity/TownActivityActionSettlementRuntime.gd（完成/失败/续接/关闭）
  └─ 被动需求    activity/TownPassiveNeedAdvancementRuntime.gd（周期性饥饿/精力/社交需求）
```

**活动与动作的区别**：动作是单次意图（去/搭话），活动是持续过程（做工/吃饭/演出），
有 `perform` 步骤、例程、预约、出席，结算走活动专用生命周期（`TownActivityLifecycleCommitRuntime`）。

## 4. ★加一个新动作/新玩法的全链路检查清单

以"给居民加一个'盘问'动作"为例，**8 步全链路，缺一环就断**：

1. **动作类型注册**：`action/TownActionTypeRegistry.gd` 的 `ALL_TYPES` 加 `"盘问"`；
   判断它是否冲突类（即时结算不进推进）还是普通动作（走推进循环）
2. **合同字段白名单**：`agent/contract/AgentContractAction.gd` 的 `ACTION_FIELDS` 加 `盘问` 的必填字段
   （目标居民/【可选】追问内容…），否则 LLM 提交必被拒
3. **动作菜单（提示词侧）**：`agent/prompt/AgentPromptCompiler.gd` 的 `_build_dynamic_context`
   给警察身份开"盘问"动作（按身份分流，参考狼人杀技能的注入方式）
4. **七表全覆盖**：对照 `TownActionTypeRegistry` 的 `TABLE_TYPES`，把新动作放进正确的表
   （字段白名单必加；必填校验若需逐类型校验则加；T7 文案 `TownActionProjection` 加 default_doing）
5. **世界执行器**：确认入口走哪条管线——普通动作 → `action/TownActionPreparationRuntime` +
   结算；有副作用的玩法 → 对应领域 Runtime（如盘问往往复用 `conversation/` 域）
6. **结果契约**：`world/contract/TownWorldResultShapes.gd` 补盘问结果形状
7. **表现层**：`world/presentation/`（如 `TownActionPresentationSemantics.gd`）加 UI 文案/表现，
   UI 才显示得出来
8. **回归测试**：`tests/` 加用例（动作合同测试/模拟 LLM 提交断言），并跑
   `town_world_agent_test.gd`（1,015 项）+ 活动套件（1,551 项）+ 架构守卫

**旧版踩坑记住**：警察"制服"曾因 **kill 别名**（合同动作名不一致）被拦；动作类型差集曾因
七表不一致漂移。**Registry 单一事实源 + 逐表比对测试**就是为了防这两类问题。

## 5. 狼人杀动作的落点（本文可对照的真实玩法）

| 动作 | 类型 | 实现 |
|---|---|---|
| 暗杀 | 普通动作（周期可推进） | `world/runtime/TownWerewolfRuntime.gd`（夜间可用/额度/暂时不公告死讯） |
| 制服 | 普通动作 | `TownRoleSkillRuntime`（警察额度 `POLICE_CHARGES_MAX=2`、制服后 `SUBDUE_SUSPENSION_MINUTES=180` 停摆） |
| 投票放逐 | 普通动作 | `TownWerewolfRuntime.start_vote_round`（08:00 起/12:30 开票，经决策附件 `exile_vote`） |
| 使用技能 | 普通动作 | `TownRoleSkillRuntime.NIGHT_SKILLS`（医生守诊/学者查验/卧底嫁祸，晚上互不干扰） |
| 追踪 | 普通动作 | 警察定位器（`POLICE_DEVICE_TRACKER`，有效期 `POLICE_DEVICE_DURATION_MINUTES=1440`） |
| 查案 | 普通动作 | `diag_police_investigate*.gd` 验证过的警察调查链 |
