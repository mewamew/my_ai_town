# 第 2 层：世界数据模型精讲（新架构版）

> 目标：理解小镇的居民/地点/活动/工作链数据从"authoring 源"到"运行时只读"的构建与校验流程，
> 以及狼人杀/身份系统该往哪加数据。
>
> 对应文件（新架构）：`game/world/data/town/`（catalog + 烘焙工具，30 个 .gd + 4 个 json）
> + `game/world/maps/`（地图运行时）+ `game/world/contract/`（结果契约）
>
> **架构变化**：旧版 data 是 `world/data/town/source/` 15 个 authoring JSON 直接烘焙；
> 新版烘焙器拆成 Builder/Validator 两族（先构建后校验），且地图/室内单独成 `maps/` 域。

---

## 总览：数据的三层

```
authoring 源（可手改） → 构建器(build) → 校验器(validate) → 运行时只读（game 运行时直接读）
   可读的 JSON/定义          TownWorld        TownWorld           town_world.json /
                            DataBuilder       DataValidator       resident_catalog.json
```

**铁律**：
1. 运行时只读烘焙产物（`town_world.json` 等），**改玩法先改 authoring 源再重新烘焙**
2. 校验器与构建器分离：`TownWorldDataBuilder` 负责组装，`TownWorldDataValidator` 负责断言，
   两者共同受 `TownWorldScalars` 的纯函数工具支撑
3. 居民定义 `resident_catalog.json` 运行时直接读（不是烘焙产物），改居民人格/职业/兴趣改它

## 1. 数据文件全景（`game/world/data/town/`）

| 文件 | 类型 | 内容 |
|---|---|---|
| `resident_catalog.json` | ★直接读 | 居民定义：persona(人格)、职业、兴趣、欢迎语、作息 */
| `town_world.json` | 烘焙产物 | 地图/地点/活动/工作链/道具 的运行时权威数据 |
| `work_chain_catalog.json` | 烘焙源 | 工作链定义（职业→任务步骤） |
| `interest_catalog.json` | 烘焙源 | 兴趣清单（与 resident_catalog 的兴趣引用） |
| `TownWorldDataBuilder.gd` | ★构建 | 把源数据组装成 town_world.json |
| `TownWorldDataValidator.gd` | ★校验 | 对构建产物做一致性断言 |
| `TownWorldCatalogBuilder/Validator.gd` | 构建/校验 | 更细分的 catalog 管线 |
| `TownWorldDataBuild.gd` | 入口 | 命令行/工具入口，跑 build+validate |
| `TownWorldScalars.gd` | ★纯工具 | 全项目共享的静态纯函数（见下） |
| `TownAuthoringFiles.gd` | 路径表 | authoring 源/产物/备份的路径常量 |
| `TownInterestCatalog.gd` / `TownWorkChainCatalog.gd` / `TownWorkContentCatalog.gd` | 读取器 | 兴趣/工作链/工作内容运行时读取 |
| `TownWorldActivityCatalog.gd` + `TownWorldActivityValidator.gd` | 读取/校验 | 活动目录 |
| `TownResidentConditionCatalog.gd` + `TownResidentConditionActivityProfiles.gd` | 读取 | 身体状态/病况目录（含各病况的活动限制画像） |
| `TownPortalCatalog.gd` | 读取 | 传送门目录 |
| `TownRouteNetworkBuilder.gd` / `TownRouteNetworkAuthoring.gd` / `TownRouteNetworkBuilder` | 构建 | 路径网络（室外）构建/校验 |
| `TownRouteQuery.gd` / `TownWorldRouteQuery.gd` | 查询 | 运行时路径查询 |
| `TownWorldMovementValidator.gd` / `TownWorldCharacterMovementQuery.gd` | 校验/查询 | 移动合法性 |
| `TownWorldPropQuery.gd` / `TownWorldPropValidator.gd` | 查询/校验 | 道具 |
| `TownOutdoorMovementClearance.gd` / `TownIndoorMovementClearance.gd` | 数据 | 室内外移动净空 |
| `TownOutdoorPerceptionAuthoring.gd` / `TownOutdoorPerceptionValidator.gd` / `TownOutdoorSurfaceMask.gd` | 数据 | 室外感知/表面遮罩 |
| `TownIndoorPropAuthoring.gd` / `TownIndoorPropPathQuery.gd` | 数据 | 室内道具 authoring |
| `TownPlaceActivityCapabilityContract.gd` | 契约 | 地点-活动能力约束 |

**`TownWorldScalars.gd` 常用纯函数**（写校验/新玩法时直接复用）：
- `exact_keys(value, expected)` / `exact_keys_sorted` —— 字典键精确校验（合同层同款）
- `contains_cjk(text)` —— 中文检测
- `is_valid_clock(clock)` / `is_ascii_digit` / `is_integer_number` / `is_number` —— 字面量校验
- `resident_id_is_safe(resident_id)` —— 居民 ID 安全校验（防路径穿越，存档/记忆都靠它）
- `polygon_area` / `sorted_dictionaries` —— 几何/排序工具

## 2. 居民数据 resident_catalog.json（狼人杀改造入口）

每个居民一个条目，关键字段：
- `resident_id` —— 稳定 ID（如 `resident_xie_mian_01`），**不可变**，存档/记忆/关系全用它
- `persona` —— 人格描述（system 提示词的人设基线）
- `occupation` —— 主职业；`interests` —— 兴趣（对齐 interest_catalog）
- 欢迎语/形象等表现字段

**狼人杀身份目前不放在 catalog 明文里**（防 LLM 直接读到），而是：
- 警察 `resident_wen_xu_01 闻叙`、卧底 3 人（`resident_xie_mian_01 谢眠`/
  `resident_qiao_yiming_01 乔一鸣`/`resident_hanako_01 花子`）、医生 `resident_bai_zhi_01 白芷`、
  学者 `resident_xu_zhao_01 许照` 的**身份常量硬编码在** `world/runtime/TownWerewolfRuntime.gd` /
  `TownRoleSkillRuntime.gd`（DOCTOR_ID/SCHOLAR_ID 等）
- 角色提示词在 `prompts/roles/police.md` / `undercover.md` / `resident_<name>.md`
- 开局时 `agent/soul/AgentSoulProfile.gd` 做一次性 OC 分析，身份倾向经编译注入，
  但**关系只作"未确认线索"**——必须真实事件才沉淀成世界事实

## 3. 地图与室内（`game/world/maps/`）

| 文件 | 职责 |
|---|---|
| `town/Town.gd` + `town/TownBase.gd` | 小镇场景根（地形/出生点/路径网络接入） |
| `town/interiors/InteriorRoom.gd` / `InteriorRoomGeometry.gd` | 室内房间与几何 |
| `town/interiors/InteriorFurnitureRuntime.gd` | 室内家具运行时 |
| `town/interiors/InteriorWallOcclusion.gd` | 墙壁遮挡（人物脚点进多边形→前景上移） |
| `town/interiors/InteriorFloorProfiles.gd` | 楼层剖面 |
| `town/interiors/redesign_v2/common/InteriorAssetGeometry.gd` | v2 室内资产几何 |

室内布局数据由 `runtime/prop/TownIndoorLayoutRuntime.gd` + `TownIndoorLayoutProjection.gd`
（runtime 根）承载；玩家或机制改室内布局走 `prop/TownIndoorLayoutCommandRuntime.gd`
（校验 `PackedStringArray` 类型契约）

## 4. 结果契约（`game/world/contract/`）

- `TownWorldContract.gd` —— 世界公开入口的返回契约
- `TownWorldResultShapes.gd` ★—— 动作结果/社会结果的结构定义
  （`completed/rejected/interrupted/replaced` 4 态 + 各领域结果形状）

**新玩法加数据时**：新动作/活动的结果形状要在这里补契约，否则表现层与记忆层拿不到正确字段。

---

## 5. 对狼人杀改造的意义

1. **新身份/新职业**：catalog 加居民或改职业 + `prompts/roles/` 加人格文件 +
   `TownRoleSkillRuntime.gd` 注册技能常量（技能 ID/次数上限/生效时段）
2. **新地点（警察局）**：地图加场景 + authoring 源加地点/路线 + 重新烘焙 +
   `TownWorldPropValidator` 校验道具 + 活动目录加"警局活动"
3. **新公告/大会**：数据层不用改，逻辑全在 `social/` 域与 `TownWerewolfRuntime`
4. **新增玩法的数据链路口诀**：authoring 源 → Builder 组装 → Validator 断言 → 运行时只读 →
   结果契约 → 表现投影（`world/presentation/`）——任何一环缺了都会在运行时报"找不到/不合法"

## 本层作业

1. 打开 `game/world/data/town/TownWorldDataValidator.gd`，找一处它校验的内容，想想要加一个新地点
   需不需要改它
2. 打开 `game/world/data/town/resident_catalog.json`，数一下居民数量、列出现在有哪几种职业
3. 打开 `world/runtime/TownWerewolfRuntime.gd` 的常量区，把身份 ID 与时间常量抄一遍
   （这是狼人杀改造的"数据真相"）
4. 跑一次数据构建：`& "F:\tools\godot\Godot_v4.7.1-stable_win64_console.exe" --path "F:\my_ai_town_upstream\game" --headless --script "res://world/data/town/TownWorldDataBuild.gd"`（如入口名不符以代码为准）
