## 二、机制：为什么会有「准备卡死看门狗」

### 2.1 决策准备是分帧进行的

`game/world/runtime/TownAgentWakePreparationRuntime.gd` `_advance_preparation`（L192-524）：

一次 wake 要依次拼装 15+ 个 stage：

```
nearby → travel → life → visible_props → available_props → activities → place
→ conversation_context → conversation → conversation_services(逐场所服务循环)
→ conversation_adapt → conversation_query → social → finalize
```

**每渲染帧只推进一个 stage**（单请求完成至少 15-40 帧）。

### 2.2 泵送是严格串行的

`game/world/integration/TownWorldAgentGateway.gd`：

- `pump_frame_budgeted`（L699-726）：每帧只消费「队头」一个工作单元；未就绪的条目重排回队尾（`readyAfterProcessFrame = frame+1`）。
- **队列里有 N 个居民同时 pending 时，队尾居民每 N 帧才轮到一个 stage**。

### 2.3 看门狗

`TownWorldAgentGateway.gd`：

- 常量 `REFRESH_PREPARATION_STALL_FRAMES := 300`（L48）。
- `_queue_agent_preparation`（L2160-2192）：首次入队即记录 `refreshStartedAtFrame`，重排不重置（防计数归零）。
- `_advance_agent_preparation`（L2195-2268）：`refresh_elapsed_frames > 300` → `_abandon_stalled_preparation`（L2271-2327）→ 丢弃这条决策并 `_submit_continuity_fallback`（L2981，台词「我先停一停，看看周围再作打算。」）。

### 2.4 触发公式

```
并发 pending 决策数 N × 每请求 stage 数(15~40) > 300 帧
→ 队尾决策必然被看门狗丢弃
```

约等于：**同时有 10 个以上居民 pending、每个 30+ stage 时踩线**。

### 2.5 卡死循环的形成

```
看门狗丢弃 → fallback 提交「待着」 → 世界接受并建立动作
→ 生活节奏/狼人杀机制 3-5 分钟后再次唤醒该居民
→ 新 decision 重新入队尾 → 前面还有同批 pending → 再次 >300 帧
→ 再次被杀 → 无限循环，全镇泵被占死
```

### 2.6 看门狗不能删

`TownWorldAgentGateway.gd` L2234-2236 注释明确：没有看门狗，卡死条目会无限重排回队尾、`pump_frame_budgeted` 每帧 return 1 永不执行 `pump(1)`、**全部新请求被饿死**——历史断点局「第 5-7 天大会候选恒 11 人」就是该症状。**看门狗是保护机制，不是 bug**；真正要解决的是让它不被触发。

## 三、根因

### 3.1 第5天凌晨的引爆点：狼人杀「全镇强制唤醒」

`game/world/runtime/TownWerewolfRuntime.gd`：

| 时机 | 唤醒方式 | 位置 |
|---|---|---|
| 天亮 08:00 | `for resident in _resident_order: _schedule_decision(resident, true)` 全员 | L330-332 |
| 11:00 投票开始 | 全体在世居民 `_schedule_decision(resident, true, ..., wake_while_current_action=true)` | L381-391 |
| 12:00 补投 | 尚未投票者全体唤醒 | L397-415 |
| 胜负 | 全员唤醒 | L704-706 |

叠加：
- 夜间 conflict attack 高频唤醒（日志 16:46:47 乔一鸣/谢眠互相「收到选项: attack→对方」，16:46:59 谢眠暗杀乔一鸣）；
- 工作坊户主罗远夜间也持「调整营业」等选项反复被调度。

→ **同一时刻 pending 的居民数（约 10）× 每请求 stage 数（15-40）逼近/超过 300 帧预算线**，第5天凌晨 02:59 全链崩塌。

### 3.2 「越到后面越卡」的渐进原因

- 狼人杀机制（投票/夜间技能/暗杀/查案/期限处决）使每天事件量、冲突唤醒数、决策数持续上升；
- 每游戏分钟 tick 工作量随天数叠加（`TownWorldAdvanceRuntime.advance` L91-148 每 tick 跑 14+ runtime 的 advance_all）；
- 帧负载上升 → 帧率下降 → 「300 帧」看门狗的墙钟时间被拉长（300 帧 @30fps=10 秒，@15fps=20 秒），体感更卡；
- 单决策耗时未变（10-12s 恒定）证明模型通道没堵，堵的是**世界侧准备泵 + 并发唤醒风暴**。

## 四、候选修复方案（按优先级，均未实施）

> 共同原则：不动官方 gateway 限流、投票快速通道、角色留档、refresh 看门狗等防漂移红线。

### 方案 A：泵送提速（治标，风险低）

`pump_frame_budgeted` 当前每帧严格推进 1 个 stage / 1 个工作单元 → 放宽为每帧推进 2-4 个 stage（或每帧处理多个队头条目），直线降低 `N × stage` 总帧数。

- 优点：改动集中在 `TownWorldAgentGateway.gd` 单文件，不动调度语义；
- 风险：每帧工作量上升，需控制在帧预算内（用 `AI_TOWN_UI_FRAME_PROBE=1` 验证不超帧）。

### 方案 B：狼人杀唤醒错峰（治本，推荐优先验证）

`TownWerewolfRuntime` 的天亮/投票/补投「全镇 `_schedule_decision`」改为**分批**唤醒：按 `_resident_order` 分 2-3 批、每批间隔 2-3 帧，避免全镇同帧 pending 挤爆准备泵。

- 优点：直接消除并发峰值，且不影响任何单个居民的行为语义；
- 风险：需要改 `TownWerewolfRuntime.gd` 三处唤醒循环 + 复用现有 `_schedule_decision` 的 defer 机制。

### 方案 C：冲突唤醒加冷却（治本辅助）

attack 选项引发的反复唤醒（夜间互见攻击目标）加最小间隔（如同一居民 10 游戏分钟内不因 conflict 重复唤醒），压低常规并发基数。

### 方案 D：看门狗阈值动态化（兜底）

`REFRESH_PREPARATION_STALL_FRAMES` 与帧率/队列长度挂钩：帧率低时阈值按真实时间等价拉长（如始终给 5 秒墙钟预算），避免低帧率下误杀；同时保留上界防饿死。

- 注意：这是兜底而非根治，不能单独作为最终方案。
