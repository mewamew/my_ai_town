# 存档迁移手册

这份手册规定小镇版本更新时如何保证旧存档可以继续游戏。存档兼容不是发布后的补救工作，而是改变存档引用含义时必须随改动完成的检查项。

开发前先查阅 `docs/持久化模块清单.md`，确认改动影响的字段、存储位置、版本组合和静态引用。

历史样本的来源、校验方式和覆盖缺口见 `docs/历史存档样本.md`。

## 兼容政策

- 当前承诺支持 beta1 至 beta6；从 beta6 起，每个发行版都进入兼容范围，并在发版时归档由对应写入器生成的完整样本。
- 强制迁移 World、Agent、居民记忆、session config、world log、照片和自定义居民库；Provider 配置、声音和显示设置尽力迁移。
- API Key、设备标识、锁、claim 和临时事务不迁移。未知的更高版本只读识别，并拒绝改写。
- 旧存档必须先检查并备份，再迁移到新的 beta6 修订；任何失败都不能改写原存档。
- 只有维护者可以明确调整支持范围，并同时记录保全方式；不能通过删除已发布迁移静默停止支持。
- 无法取得玩家原档。历史兼容只以 Git tag、发行提交和对应写入器重建的完整磁盘存档为依据；文档与测试必须明确这一证据边界，不能把重建档称为玩家原档。

## 强制规则

- 只要修改了存档中会引用的活动、活动位置、道具名称、位置锚点、角色、效果、任务状态或任何模块的存档字段，就必须同时检查旧存档迁移。
- `sourceFingerprint` 只能发现编译数据发生过变化，不能自动把旧活动、旧道具或旧锚点转换成新定义。需要转换的字段必须登记明确的历史迁移规则。
- 已经随版本发布的迁移规则不能删除。跳过多个版本读取存档时，迁移要能够按旧指纹逐段执行到当前版本。
- 迁移必须在当前编译数据的严格校验之前执行，并且可以重复执行。迁移后的存档要使用当前指纹重新保存。
- 不能对整个存档做没有上下文的全局文字替换。同一个道具名称可能仍被其他活动或历史任务合法引用，规则必须同时限定活动 ID、位置 ID、目标类型和动作。
- Windows 存档路径必须按传统 260 字符边界设计，不能依赖玩家开启系统长路径选项。临时锁、事务所有者、Agent 快照、会话照片、正式归档和居民运行时记忆的写入中间文件不得继续叠加在深层业务路径下，必须使用浅层、固定长度的目录或文件名。
- 任何存档目录、会话 ID、事务 ID、锁名或临时文件命名变更，都必须运行超过 260 字符的 Windows 路径回归，覆盖创建、写入、恢复、重新读取和递归清理；不能只在 macOS 上验证成功。
- 路径兼容修复不能删除或改写已经提交的存档主体。遇到临时事务残留时，应保留已完成且哈希一致的存档修订，只回收可以确认不再被活动进程持有的临时状态。

## 兼容注册表

`TownSaveCompatibilityRegistry.gd` 是 beta1 起的历史兼容账本，负责模块分层、版本识别、相邻发行版迁移边、支持状态和稳定错误码；`TownSaveSchemaRegistry.gd` 继续保存具体字段迁移。

- `module_descriptors()`：返回 15 个迁移单元的层级、策略、当前版本和支持范围。
- `detect_release(evidence)`：根据模块版本、World 区段数、活动指纹和居民路径布局返回精确发行版或合法版本范围；模块版本来自磁盘中的 profile、manifest、World、World Data、Agent 和居民载荷，可信的样本来源记录只能缩小已经匹配的范围。
- `migration_path(from, to)`：返回逐版本迁移边和当前按内容判断的幂等迁移；无字段变化的发行边也必须登记 `no_change` 和原因。
- `TownHistoricalSaveUpgrader.upgrade(source, publication)`：按账本恢复旧修订，通过现有成对保存事务发布新的 beta6 修订，再由启动目录复验 World 与 Agent；原修订保持只读。
- `TownSessionUiService.restore_discovered_revision(...)`：正式继续游戏与历史矩阵共用的恢复入口；当前版直接恢复，已登记旧版升级后恢复，未来版和未知组合只读拒绝。
- `validate_registry()`：检查模块、版本、发行顺序、迁移链和错误码是否完整。

beta3 至 beta6 的磁盘契约相同，无法精确识别时，账本从 beta3 返回完整的相邻版本路径；导入器实现后必须按该路径执行幂等迁移。未来版本返回只读状态；过旧版本、未知组合、文件损坏和迁移链缺失分别使用不同错误码。

## 标准流程

1. 在 `docs/持久化模块清单.md` 登记发行版的字段、路径、版本组合、指纹，以及迁移或“无需迁移”声明。
2. 在修改活动或世界数据前，保存修改前生成的 `town_world.json` 中对应 `activityIntegrationReceipt.sourceFingerprint`；修改后重新生成并记录新的指纹。
3. 在 `game/world/presentation/session/TownSaveCompatibilityRegistry.gd` 登记相邻发行版迁移边、受影响模块、迁移 ID，或明确登记 `no_change` 及原因。
4. 在 `game/world/presentation/session/TownSaveSchemaRegistry.gd` 实现旧指纹到新指纹的精确字段规则；规则需要说明旧值、新值以及最小匹配范围。
5. 在对应模块的 `prepare_restore` 入口调用统一迁移表，然后再执行当前定义的字段、占用关系、效果和幂等性校验。
6. 为每条迁移至少补一条旧存档回归测试，覆盖本次实际受影响的状态。若改动涉及进行中的执行、reservation、未完成任务或已结算效果，要分别覆盖这些状态。
7. 验证“旧存档读取成功 → 按当前定义继续 → 再保存”的闭环，并检查重新保存后的存档只包含当前引用，不再保留旧值。
8. 归档本次发行版写入器生成的完整样本，并记录来源、场景、版本组合、指纹、校验值和预期升级结果。
9. 在同一批次更新 `更新日志.md`，说明玩家可见的旧存档兼容修复；打包时把更新日志放进玩家收到的压缩包。
10. 如果改动涉及文件或目录布局，运行 `windows_directory_cleanup_test.gd`，确认恢复事务锁、槽位事务锁、Agent 快照、会话照片、正式归档和居民运行时记忆的旧式深层临时路径会超过 260 字符，而当前临时路径仍处于边界内并能完整写入、读取和清理。

PR 修改持久化字段、引用、目录或事务实现时，还要新增 `docs/persistence-changes/*.json` 声明。声明必须说明需要迁移或无需迁移，并列出受影响模块、迁移编号、样本、测试和文档；缺项时 `persistence_change_check.py` 会让 CI 失败。

beta1 至 beta6 的兼容闭环由 `run_historical_save_migration_matrix.sh` 验证。beta1 至 beta5 通过正式恢复入口发布 beta6 新修订；beta6 直接继续，不产生迁移修订。每个样本随后都会继续运行、再次保存并由新 Runtime 重开。目录会先只读提取各模块的真实版本，再进行 Agent 和居民状态解码；未来发行版、未来模块和未知字段组合均拒绝恢复，也不会生成坏档修复计划。

## 当前坏档修复闭环

`TownStartupSaveCatalog` 负责只读校验；`TownSaveRecoveryPlanner` 只根据校验结果生成检查报告和计划。最新修订损坏且存在较旧的完整 World + Agent 配对时，玩家确认后恢复该配对，并通过现有成对保存事务发布新修订。

`TownSaveReconciliationService` 处理保存或恢复中断：先核对事务日志、已发布 manifest 和 Agent 快照，再由玩家确认封口。已提交但未发布的 Agent 快照只保留为证据，不与其他 World 修订拼接；恢复中断只有在 manifest、World、world log、session config、Agent 居民集合均完整时才能结束。协调只追加 `save_reconciled` 或 `restore_reconciled` 记录，不覆盖原日志；中途失败可用同一计划继续，已完成项不会重复写入。

使用旧完整配对执行安全修复时，正式发布事务会同时重建 manifest 索引、session config 投影和启动摘要；这些派生数据不从损坏修订猜测。修复回执在 `rebuiltDerivedData` 中记录实际重建项。

没有完整配对或无法证明提交状态时停止修复，页面提供稳定诊断编号和“导出诊断”入口。导出内容不包含居民载荷或密钥，原存档保持不变。确认页按实际计划显示“重新诊断”“执行修复/导出诊断”“仅返回”。manifest、session config、World、world log、Agent 任一组件独立损坏均进入同一套判断。

## 当前已登记迁移

### 2026-08-24 地点服务协调者补齐

当前地点服务会从现任职员中派生当班协调者；旧存档在同一岗位有多名职员时保存为空。恢复时只在地点、岗位、容量、活动引用等配置与当前定义完全一致时补齐 `owner_id`。若旧状态从未改动，`open` 随当前默认值更新；玩家已经改过营业状态时保留原值。配置不一致仍按坏档处理。迁移 ID 为 `2026-08-24-place-service-owner-backfill`；beta1 至 beta6 都会按内容守卫执行，因此 beta6 存档也不会漏掉。

铺面负责人现由职业岗位派生。旧 Agent 居民载荷中，只有 `owner_resident_id` 指向本局居民且姓名与 `owner` 一致的铺面会把两者改为 `null`；住家、公共地点、虚构引用和异常字段不改。迁移 ID 为 `2026-08-24-shop-owner-derived-from-occupation`。恢复总回执的 `moduleReceipts` 分别保留 World 与 Agent 的迁移版本和编号。

### 2026-08-10 公共食堂活动目标和服务容量调整

提交 `543c40b` 调整了公共食堂的递餐和准备面团目标位置，并把公共食堂服务容量从 2 调整为 4。旧版已完成或进行中的活动执行仍然记录 `公共食堂备餐柜`，当前活动定义分别使用 `公共食堂递餐口` 和 `公共食堂面团操作台`；旧版地点服务状态仍记录容量 2。迁移只对以下明确字段进行升级：

- 活动：`activity_baker_prepare_dough`
- 位置：`slot_baker_prepare_dough_01`
- 目标类型：`prop`
- 动作：`准备面团`
- 旧目标：`公共食堂备餐柜`
- 新目标：`公共食堂面团操作台`
- 活动：`activity_dining_serve_meal`
- 位置：`slot_dining_serve_meal_01`
- 目标类型：`prop`
- 动作：`取餐`
- 旧目标：`公共食堂备餐柜`
- 新目标：`公共食堂递餐口`
- `placeServiceStates.公共食堂.service_capacity`：`2` → `4`

对应迁移 ID 为 `2026-08-10-public-dining-prepare-dough-target`，实现和历史指纹登记在 `TownSaveSchemaRegistry.gd`。食堂取餐活动仍然合法使用 `公共食堂备餐柜`，因此不能把这个名称从整个存档中批量替换。

## 发布前检查项

每次涉及存档引用的版本更新，都要完成以下检查：

- [ ] 找到修改前、修改后的源指纹，并确认迁移链可以从已支持的历史版本走到当前版本。
- [ ] 持久化清单已记录字段、路径、版本组合，以及迁移或“无需迁移”声明。
- [ ] 迁移规则只匹配明确的业务身份，不依赖显示名称的模糊搜索。
- [ ] 对应发行版的完整磁盘样本已归档，并记录来源、场景、指纹、校验值和预期结果。
- [ ] 历史存档恢复测试通过，且测试包含至少一个真实受影响的字段。
- [ ] 旧存档恢复后重新保存，检查当前指纹和当前引用已经落盘。
- [ ] 存档路径或临时文件命名发生变化时，Windows 超长路径创建、恢复和清理回归已经通过。
- [ ] Windows runner 已通过 `save_reconciliation_test.gd`、`windows_directory_cleanup_test.gd`，并完成 beta5 长路径样本升级、继续、再保存和重开。
- [ ] 运行 `tools/guards/run_guards.sh`。
- [ ] 运行与改动范围匹配的 Godot 无头测试，并确认测试后源码目录没有意外变化。
- [ ] 更新根目录 `更新日志.md`，打包时复制到最终压缩包。
